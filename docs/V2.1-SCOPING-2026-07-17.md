## 0. The one-paragraph answer

The council's HTTP verdict is correct and the code confirms it: an HTTP proxy
that terminates auth and passes a `caller_id` down the stdio pipe recreates the
exact spoofing shape `Host/ReceiptIdentity.lean` already refutes — the field is
request-derived on a pipe that still satisfies `StdioTotal`, so `forgeable_echo`
applies verbatim and every existing caller-relevant proof goes vacuous while the
whole proxy enters the TCB. **That route is a trap; do not build it in that
form.** The sound multiplexed path is the signed principal envelope over stdio
(design note option 3), and — the load-bearing feasibility fact — its formal
skeleton **already exists in the codebase**: `credentialed_topology_authenticates`
(`Host/ReceiptIdentity.lean:324`) proves that on a credential-constrained send
relation an authenticator exists. Route 2 instantiates existing theory; it does
not invent new theory. Its real costs are not the theorems (two of the three
obligations are Fable-provable, the third is half-proof half-named-seam) but the
plumbing the design note under-prices: extending `CanonicalAction` ripples
through the spelled-plan proofs and tripwires, a new policy-vocabulary section
forces a fleet-wide wasm repin, and mixed-mode (unauthenticated caller meets
principal-scoped kernel) is an unforced design decision that must land
fail-closed. Recommended sequencing: ship the process-isolation doc now (~1–2
days), optionally the config-pinned-principal mini-brick (~2–4 days, near-rfl
theorems), build the envelope only on real demand (~2–4 weeks including the
Budget MVP), and treat HTTP as untrusted plumbing to be added *after* the
envelope exists, if ever.

## 1. Ground truth from disk (what the analysis stands on)

Facts checked directly, cited by file/line so Monkey can frisk them:

1. **The no-go is universal and structural.** `stdio_no_caller_authentication`
   (`Host/ReceiptIdentity.lean:286`) proves: under `StdioTotal` (`:259` — every
   caller can emit every byte string, the deployed topology per
   `main.rs` `Stdio::piped()` at `:587-588`), NO function of everything the host
   holds at dispatch time is a sound `CallerAuthenticator` (`:266`). Two
   companion theorems sharpen it: `forgeable_echo` (`:299` — any request-derived
   field is an echo with zero authentication weight) and
   `credential_excludes_totality` (`:309` — a binding credential is
   *incompatible* with `StdioTotal`, so caller identity is a topology change,
   not a receipt field).
2. **The escape hatch is already a theorem.** `credentialed_topology_authenticates`
   (`:324`): if the send relation is credential-constrained (each request
   determines its sender via a credential), an authenticator exists — read the
   credential. And `caller_authenticator_satisfiable` (`:339`) shows the
   definition has teeth. **This is the formal foundation Route 2 stands on,
   today, with zero new theory.**
3. **Ed25519 verification is already wired into Lean.** `verifyConfigSignature`
   (`Host/Config.lean:162-165`) calls `SealV2.ed25519Verify` (an `@[extern]`
   leaf) to verify the trusted-config envelope; approval tokens verify against a
   second root. A request-path envelope adds a *new call site of an existing
   trusted extern*, not a new crypto dependency.
4. **The freshness pattern exists.** The Rust host already runs an A3
   nonce/replay/TTL filter with a sqlite replay store for approval records
   (`rust/src/a3.rs`, `rust/src/replay_store.rs`, wired in `main.rs:560-580`).
   Request-envelope freshness can follow the identical seam.
5. **The faithfulness-seam idiom exists.** `IdentityFaithful`
   (`ReceiptIdentity.lean:233`) is the named, never-an-axiom TCB seam ("what
   Rust wrote equals the model value"), discharged operationally by
   `rust/tests/receipt_identity.rs` including a mutation drill that plants a
   request-derived `caller_id` and watches the test refuse it. A receipt
   `principal` field would need its own twin (call it R-PRINC).
6. **The kernel plumbing is uniform and spelled.** `registryFor` (`Ffi.lean:87`)
   wires seven kernels off `TrustedConfig` sections; `stepImpl_spelled`
   (`Ffi.lean:354`) proves the whole marshalling is a pure plan around two IO
   leaves; `FfiSpec.lean` pins `registryFor_kernels`. Budget is
   `Kernels/Budget.lean` over the proven `BudgetCore` automaton
   (`run_never_over_budget`, `BudgetCore.lean:57`), with state keyed by budget
   *name* only (`BudgetState := List (String × BState)`, `Budget.lean:32`).
   There is no principal anywhere in the decision plane — the design note's
   premise is accurate.
7. **FFI exports are not thread-safe** — stated in `Ffi.lean:29-31`; the Rust
   host serialises on a single mediation thread. Any concurrent transport must
   preserve that serialisation.

## 2. Track A — transport, four routes head-to-head

### Route 1 — HTTP transport with an auth-terminating proxy

**The council's trap, answered directly: yes, and the code says exactly why.**

If a proxy terminates mTLS/bearer auth and passes `caller_id` down the stdio
pipe, then from the kernel's standpoint the proxy→kernel segment still
satisfies `StdioTotal`: the kernel receives bytes on one uncredentialed pipe and
cannot distinguish "the proxy honestly relayed Alice's authenticated identity"
from "anything that can write to this pipe claimed to be Alice." `caller_id` is
then a request-derived field, and `forgeable_echo` applies **verbatim** — it is
precisely the `spoofingAssigner` shape `Host/Provenance.lean` refuted, now
wearing a TLS costume.

Two precise consequences, worth stating carefully because they are subtly
different:

- **The existing proofs do not become false — they become vacuous for the
  caller claim.** `receipt_identity_separated`, the boot-constant theorems, the
  no-go itself: all still hold. But none of them says anything about the new
  `caller_id`, and the no-go actively says the kernel *cannot* say anything
  about it. The machine-checked story stops at the pipe.
- **All authentication weight moves into the proxy, i.e. the TCB expands from
  "Lean runtime + thin Rust marshalling" to the entire proxy**: its TLS stack,
  HTTP parser (request smuggling, header injection), session/connection
  multiplexing logic, credential cache, and its own key custody. Every one of
  those is now a soundness dependency with zero Lean coverage. For a project
  whose entire value is a small proven TCB, this is self-refuting.

**Can the Lean kernel stay the verifier over HTTP?** Yes — but only if the
signed credential itself reaches the kernel and the kernel verifies it. At that
point the design note's sharpest line is confirmed by the code structure: **the
HTTP transport is irrelevant to the security proof** (the binding theorem never
mentions the wire), and Route 1 collapses into "Route 2 + a large transport
build." The transport build is genuinely large:

- **Rust changes:** a new HTTP server (hyper/axum or hand-rolled), MCP
  streamable-HTTP transport conformance, TLS termination, connection lifecycle.
  The current host is a ~1,100-line single-threaded stdio MITM; this is a
  different program.
- **Concurrency:** the Lean FFI exports are not thread-safe (`Ffi.lean:29-31`)
  and the session is one global `sessionRef` of `IO.Ref`s. Concurrent HTTP
  connections must funnel through one mediation mutex — either accept a global
  serialisation point (throughput ceiling, head-of-line blocking) or rebuild
  session state per connection (a Lean-side change this note scoped out).
- **New TCB even in the sound variant:** the HTTP layer is availability-TCB
  (it can drop/deny) but not soundness-TCB *only if* nothing decision-bearing
  is derived from it. Discipline required: no header ever reaches the decision
  plane.

**One nuance where I'd sharpen the design note (not contradict it):** "HTTP is
irrelevant to the proof" is true for the *binding* theorem but overstates the
whole. Freshness/replay (nonce windows, TTL, the replay store) stays a
Rust-side seam in every variant — same as today's A3 approvals, so no
*regression*, but the honest sentence is "unchanged named seam," not
"irrelevant."

**Effort:** 4–8 weeks *including* Route 2 as a prerequisite; the HTTP-specific
part alone is 2–4 weeks of Rust with no proof payoff whatsoever.
**Verdict: the proxy-injected variant is a TRAP — never build it. The
kernel-verifies variant is "Route 2 first, HTTP later, if ever."**

### Route 2 — signed principal envelope over stdio (the sound multiplexed path)

**Design.** The caller wraps each mediated request in an envelope: a signature
(per-principal Ed25519 key) over a canonical digest of the exact request bytes
plus a per-request nonce. The kernel verifies the signature in Lean against a
**principal registry pinned inside the signed `TrustedConfig`** (new
PolicyBundle section, e.g. `principals: [{principal_id, pubkey}]`), and derives
the principal **only** from the verified key. Anti-spoof comes from
cryptography, not the pipe.

**Why this is consistent with the no-go — the framing evaluators will poke at,
pre-empted.** The pipe remains `StdioTotal`; nothing changes about who can emit
bytes. What the envelope yields is a **partial** authenticator:
`Option AuthenticatedPrincipal`, `some P` only when a signature verifies
against P's registered key, fail-closed `none` otherwise. That is *not* a
`CallerAuthenticator` in the `:266` sense (which must name *every* sender), so
the no-go is untouched — and `credentialed_topology_authenticates` is exactly
the theorem showing the credential-constrained restriction of the send relation
admits an authenticator. **The V2.1 claim must be scoped precisely:
"authenticated principal when the envelope verifies," never "caller
authentication on stdio" — the latter remains proven impossible, and keeping
that theorem loud is a selling point, not an embarrassment.** The forgery
exclusion ("an attacker cannot make verify pass without the key") is a
cryptographic assumption riding the existing `ed25519Verify` extern seam — TCB,
never a theorem. Section 4 splits this precisely.

**Concrete Rust changes (moderate):**
- Extract envelope fields from the wire line and pass them through the step
  input JSON (the `stepImpl` marshalling gains fields; the "one binding, no
  rewrites" discipline for the judged line must extend to the signed bytes —
  the canonical digest should cover the *exact judged line*, which the existing
  single-binding structure makes natural).
- A3-style freshness for request nonces: reuse the `a3.rs` + `replay_store.rs`
  pattern (new store namespace, TTL window). This is the second A3 instance,
  not a new mechanism.
- Receipt assembler writes the `principal` field from the Lean decision output
  only; a new differential test (R-PRINC twin of `receipt_identity.rs`)
  including the mutation drill that plants a request-supplied principal and
  watches the test refuse it.

**Concrete Lean changes (the real brick — detailed in Track B):**
`AuthenticatedPrincipal` opaque type + registry config section + verification
in the parse path + Budget principal axis + three theorem families + repair of
the rippled spelled-plan proofs.

**New TCB surface, honestly enumerated:**
- **Crypto assumption at a new call site:** Ed25519 unforgeability + extern
  faithfulness, now on the *request path* (per-call rate, adversary-supplied
  inputs to the verifier — fuzz the extern boundary).
- **Nonce/freshness/replay:** Rust-side, same seam class as A3 approvals.
  Named, tested, not proven.
- **Key registry lifecycle:** custody is the caller's problem (named non-claim,
  as the design note already says: a bearer credential readable by the host
  process forges anything). Rotation = re-sign the config; revocation = config
  epoch bump. **There is no online revocation** — a compromised principal key
  stays valid until the operator re-signs config. Acceptable for the MVP if
  stated; a lie if unstated.
- **Client-side signing tooling:** a small SDK/CLI so callers can produce
  envelopes. Not TCB for the gate, but real effort and a real adoption cost.

**What breaks:**
- **Wire protocol for callers** — every caller of a principal-scoped deployment
  must wrap requests. Mixed-mode question (below) decides how hard this breaks
  existing deployments.
- **Receipt schema** — new `principal` field ⇒ receipt-verifier and any
  downstream receipt consumers update (schema version bump; there is precedent
  in the honesty-matrix v1→v2 bump).
- **Policy vocabulary** — a new `principals` section in the strict PolicyBundle
  parser (hard-errors on unknown keys, `Host/Config.lean:176`). **This is a
  fleet event the design note omits:** the bundle vocabulary is shared across
  the wasm/kit/downstream copies, so the parser change forces a wasm rebuild
  and byte-copy repin across the fleet (~1 day, mechanical, but it is N repos
  of churn and a new wasm hash to pin everywhere).
- **Mixed-mode design decision (unforced, the note skips it):** what happens
  when a request with no (or an unverifiable) envelope hits a deployment whose
  config has principal-scoped budgets? The only honest default is
  **fail-closed deny** for principal-scoped kernels. That means an operator who
  adds a `principals` section to a single-tenant deployment breaks it — so add
  a config lint (the `budgetCapsConsistent` idiom) that refuses ambiguous
  configs (e.g. a principal-scoped budget whose tools are also covered by no
  anonymous path) rather than letting the deny surprise them at runtime.

**Effort:** ~2–4 weeks total including the Track B Budget MVP, of which the
genuinely new proof content is maybe 1 week and the rest is plumbing, ripple
repair, differential tests, and fleet repin.

### Route 3 — process-level isolation

One seal instance per principal/group; OS/container identity IS the principal;
policy stays capability-keyed inside each gate. Zero code, zero proof, zero new
TCB. Deliverable is a deployment doc + optional spawner demo script. Honest
claim: "per-principal limits via separate gates." Limitations: coarse, static
per deployment, no shared-pipe multi-tenancy, N processes.
**Effort: 1–2 days.** This is available *today* and should be documented
regardless of any other decision.

### Route 4 — config-pinned principal

Operator pins `principal_id` in the signed config at spawn; the receipt carries
it as a **boot constant** — never anything request-derived. The theorem
obligation `receipt_principal_eq_config_principal` follows the
`ReceiptIdentity` idiom so exactly that the proofs are near-rfl clones:
request-separated (P-SEP at the field, the `receipt_identity_separated` shape)
and boot-constant (the `receipt_identity_boot_constant` shape), plus one small
`ofBundle` preservation lemma and an R-PRINC-lite faithfulness seam +
differential test. Since there is one principal per gate, **no kernel needs a
principal axis at all** — the whole gate is the principal's, which is why this
is cheap. New TCB: none beyond the already-signed config. It is Route 3 with a
proof-backed receipt label: a multi-agent host spawns N gates and each receipt
*names its principal soundly*.

Note a small vocabulary cost even here: `principal_id` in the config is a
bundle-vocabulary addition ⇒ the same fleet-repin event as Route 2 (though it
could ride along with any other planned vocabulary change).

**Effort: 2–4 days.** Mild disagreement with the design note's flat ordering:
this is not just "option 2 of 3" — it is the best *value-per-day* brick on the
table if any near-term principal story is wanted, because it produces a real
receipt `principal` field with sound semantics and a proven theorem for days,
not weeks, and it de-risks the receipt-schema + R-PRINC seam work that Route 2
needs anyway.

## 3. Track B — the principal axis in the kernels (Budget first)

### 3.1 `AuthenticatedPrincipal` — the opaque type

Proposed shape: a structure (or subtype) carrying its verification witness —
morally `{ p : String // ∃ cred ∈ registry-scope, verifyOk cred = true ∧
subjectOf cred = p }` — with a **private constructor** and a single smart
constructor `verify : credential → trustAnchor → Option AuthenticatedPrincipal`.
Two honest observations:

- **Un-constructibility is module discipline, not magic.** Lean enforces it via
  the private constructor + not exporting any other maker; a reviewer checks the
  module surface. That is enforceable and auditable (and pinnable with a
  build-time check that no other constructor exists), but it is an engineering
  invariant, not a metatheorem.
- **The witness bottoms out at the extern.** The `verifyOk` inside the subtype
  is the `@[extern] ed25519Verify` Bool. So every theorem quantifying over
  `AuthenticatedPrincipal` is real Lean, but its *meaning* is conditional on
  the extern computing real Ed25519 and on Ed25519 being unforgeable — the same
  seam class the config envelope already rides. New instance, not new kind.

### 3.2 Where the principal enters the decision plane — the design note's gap

This is the most important thing the note under-specifies, and it changes the
cost estimate. There are only two entry points:

1. **The Evidence/`gather` plane** (Rust gathers, Lean trusts): **this is the
   proxy trap in miniature.** If Rust verifies the envelope and hands Lean a
   bare principal string as evidence, the kernel trusts an assertion it cannot
   check and the binding theorem is about nothing. Ruled out.
2. **The Lean parse path**: verification happens inside Lean during
   canonicalisation, and `CanonicalAction` (or a new dispatch input alongside
   it) carries `principal? : Option AuthenticatedPrincipal`. This is the only
   sound entry — and it ripples:
   - `CanonicalAction` is quantified over by the P-SEP/provenance bricks, the
     receipt-identity theorems, `stepImpl_spelled`/`stepPlanFor`/`stepRender`,
     and the `registryFor_kernels` tripwires, all of which are pinned by
     `#guard_msgs` axiom pins that fail the build on drift. Most of these
     proofs are structural and will repair mechanically, but "mechanically"
     across that surface is real days, not hours.
   - The *meaning* of the separation statements shifts and must be re-scoped
     consciously: today "perturb the request arbitrarily" includes every byte;
     with a credential aboard, separation becomes "independent of every
     **non-credential** field." That re-scoping must be done loudly in the
     docstrings or an evaluator will read the old claim and find it silently
     weakened.

### 3.3 Budget changes

`BudgetState` re-keys from `name` to `(principal, name)` (or a per-principal
map of the existing state); `budgetStateFor`/`setBudgetState` take the
principal; `budgetCapsConsistent` extends (same-name-same-cap logic per
principal scope, plus the mixed-mode lint from §2). `BudgetCore` itself — the
proven automaton — needs **zero change**: the principal axis is pure state
indexing above it, which is exactly why Budget is the right first kernel.

### 3.4 The three obligations — provable vs trusted, precisely

| Obligation | Verdict | Detail |
|---|---|---|
| `principal_from_auth_not_request` | **Fable-provable** (P-SEP shape), with one honest caveat | The provable statement: the decision/receipt principal is a function of the verified credential and the config registry alone; any request whose envelope fails verification yields `none` (fail-closed); perturbing every non-credential request byte moves nothing. **What it can never say:** "an attacker cannot set the principal." It says the principal flows *only through `verify`*; that forged signatures do not pass `verify` is the crypto assumption (TCB). The report/docs must state this split or the theorem overclaims. |
| `principal_budget_isolation` | **Fable-provable, pure — the genuinely new proven content** | A structural frame lemma over the re-keyed state: a step by principal A leaves every B-keyed counter unchanged, and a spoofed request field cannot switch the debit target *because no request field reaches the debit key* (only the `AuthenticatedPrincipal` does, by construction of the type). Composes with `run_never_over_budget` per principal. Medium effort, no new axioms expected. |
| `receipt_principal_authenticated` | **Half proof, half named seam** | Lean side: "if a receipt asserts principal P, the decision's `AuthenticatedPrincipal` was P" — provable in the model. Rust side: "the assembler wrote what the model says" — a new **R-PRINC** faithfulness seam, the `IdentityFaithful` idiom (explicit hypothesis, never an axiom), discharged by a differential test against the real binary including the plant-a-spoofed-principal mutation drill. |

Config/receipt changes: new `principals` bundle section + `ofBundle` mapping +
preservation lemma (the `ofBundle_*` pattern); receipt `principal` field +
schema bump + receipt-verifier update.

## 4. PROOF vs NEW-TCB — the clean split

**Machine-checked (new or extended proofs):**
- Binding: principal is a function of verified credential + registry only
  (P-SEP shape).
- Isolation: per-principal budget frame lemma over the re-keyed state,
  composed with the existing `run_never_over_budget`.
- Receipt binding in the model; `ofBundle` preservation; config lints.
- Already on disk, reused as the foundation: the no-go pair
  (`stdio_no_caller_authentication`, `forgeable_echo`) and the escape hatch
  (`credentialed_topology_authenticates`) — Route 2 is the *instantiation* of
  an existing formal framework, which is the single strongest feasibility fact
  in this report.

**Trusted, named, never proven (new instances of existing seam classes):**
- Ed25519 unforgeability + extern faithfulness at the request-path call site.
- Nonce/freshness/replay window (Rust A3-pattern, second instance).
- R-PRINC assembler faithfulness (differential-test discharged).
- Key custody, rotation-by-re-sign, revocation-by-epoch (no online revocation).
- Client signing tooling correctness (outside the gate).

**Trusted and UNBOUNDED (why Route 1's proxy variant is disqualified):**
- The entire HTTP proxy in the auth-terminating design. Not a seam — a second
  program in the TCB with no Lean model at all.

## 6. Recommended sequencing

1. **Now:** Route 3 deployment doc (+ keep surfacing
   `stdio_no_caller_authentication` as the honesty feature it is). Cost: days.
2. **Now or on first soft demand:** Route 4 mini-brick — proven receipt
   `principal` at trivial cost; de-risks the receipt-schema and R-PRINC work
   Route 2 needs anyway. Fold its vocabulary bump into the next planned fleet
   repin rather than forcing one.
3. **On real buyer/reviewer demand only (per the plan's load-bearing
   assumption):** Route 2 MVP in the design note's order —
   `AuthenticatedPrincipal` → Budget only → binding + isolation theorems →
   R-PRINC differential test → transport choice **last**. Never thread the
   principal axis through the other six kernels before the binding theorem
   holds for Budget.
4. **HTTP:** only ever as untrusted plumbing on top of a landed Route 2, and
   only if a buyer makes it load-bearing. The proxy-injected variant is
   rejected permanently, and the rejection is itself marketable: "we proved why
   we won't do it that way" (`forgeable_echo`).

## 7. Where I disagree with (or sharpen) the council and the design note

1. **Agreement with the council's core, sharper frame:** HTTP-with-proxy does
   not make the proofs *false*; it makes them **vacuous for the caller claim**
   while relocating all authentication weight into an unmodelled proxy. Same
   verdict, more precise reason — and it is the exact `spoofingAssigner`
   pattern already refuted on disk.
2. **"HTTP is irrelevant to the proof if the kernel verifies" — mostly, not
   entirely.** True for the binding theorem; freshness/replay remains a
   Rust-side named seam in every variant. "Unchanged seam," not "irrelevant."
3. **The note under-prices Route 2 in three concrete places:** the
   `CanonicalAction` ripple through the spelled-plan proofs and tripwires
   (§3.2), the fleet wasm repin forced by any strict-parser vocabulary change,
   and the mixed-mode fail-closed decision + config lint (§2).
4. **The note under-sells Route 4.** As a receipt-bearing, theorem-backed,
   days-not-weeks brick it is the natural *first* response to soft demand, not
   merely the middle entry of a capability ladder.
5. **The note's strongest claim is confirmed and strengthened by disk:** the
   escape hatch is not a design idea — it is a theorem that already builds
   (`credentialed_topology_authenticates`, with `caller_authenticator_satisfiable`
   showing non-vacuity). Route 2's feasibility story should lead with that.
