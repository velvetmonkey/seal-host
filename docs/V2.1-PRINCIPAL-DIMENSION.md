# seal V2.1 — the authenticated principal dimension (design note)

**Status: DESIGN ONLY. No code. Build gated on real buyer/reviewer demand.**
Anchored in council `b1a6f805` (2026-07-17, harmonic, 4/4). Companion to
`POLICY-ASSURANCE-BOUNDARY.md` (the caller no-go) and `PROOF-REFERENCE.md`.

## The question

Multi-tenant / distributed policy: *different limits per caller* — Group A's
budget vs Group B's budget, per-agent quotas, per-team consensus. seal V2 cannot
do this natively, and says so honestly: every kernel keys on tool-set /
capability-id, never on *who is calling*.

## Why it is not a config knob — the no-go

On the deployed stdio topology, caller identity is a **proven no-go**:
`stdio_no_caller_authentication` (`Host/ReceiptIdentity.lean`). Every request
byte arrives through one uncredentialed pipe (`main.rs`, `Stdio::piped()`), so
any caller can emit any `caller_id`. A receipt that copies a caller field from
the request is forgeable and fails an evaluator audit. **A naming-convention
"Group A / Group B" tag is not tenant isolation.**

This negative theorem is an asset, not a gap. Surface it as a feature of
honesty: "seal refuses to ship a spoofable caller_id, and here is the proof
that a request-derived one is unsound."

## Why HTTP is NOT the fix

The tempting move is to bolt on an HTTP transport with mTLS/bearer auth. It is
the wrong move, and it is unsound as stated:

- An HTTP proxy that terminates auth and then passes a `caller_id` **down the
  stdio pipe** to the Lean kernel silently expands the TCB to include the entire
  proxy. The machine-checked stdio proofs go hollow: the kernel cannot prove the
  proxy did not lie.
- If, instead, the Lean kernel verifies the signed credential **itself**, then
  the HTTP transport is irrelevant to the security proof. The soundness lives in
  the binding theorem, not the wire protocol.

Necessary ≠ sufficient: **authenticated transport is not provably sound
principal binding.** mTLS authenticates a connection; a bearer token
authenticates possession; neither proves the receipt names the intended agent
through proxies, multiplexers, delegation, replay, or bad key custody.

## Three honest designs (least to most capable)

1. **Process-level isolation.** One seal instance per principal/group; OS or
   container identity IS the principal. Policy stays capability-keyed inside the
   gate; isolation is outside it. Honest claim: "per-principal limits via
   separate gates." Zero new proof. Coarse (static per deployment).
2. **Config-pinned principal.** Operator pins `principal_id` in gate config at
   spawn; kernels may key on that *deployment* principal, never on request bytes.
   Theorem obligation: `receipt_principal_eq_config_principal`. A multi-agent
   host spawns N gates. Still not shared-pipe multi-tenant.
3. **Signed principal envelope over stdio** — the sound multiplexed path, no
   HTTP rebuild. The caller signs a canonical request digest + nonce; seal
   verifies the signature against an out-of-band issuer key → principal registry
   and derives the principal **only** from the verified key. Anti-spoof comes
   from cryptography, not the pipe. Consistent with the no-go, which kills a
   *copied* field, not a *signature-verified subject*. Residual attack
   (replay / envelope-lifting) is killed by the per-request nonce + the issuer
   private key the caller does not hold.

## The MVP brick (option 3), if built

Smallest thing that makes per-principal policy REAL and machine-provable:

- an **opaque `AuthenticatedPrincipal`** type, un-constructible except via
  `verify(credential, trust_anchor)` — the value carries its verification proof;
  kernels and receipts take THIS type, never a raw string;
- **one** principal-scoped kernel to demonstrate: **Budget** (Group A vs Group B,
  where "forge caller → free budget" is the obvious exploit). Not all seven;
- receipt `principal` filled **only** from `AuthenticatedPrincipal`.

### Theorem obligations (the proof is where soundness lives)

- `principal_from_auth_not_request` — the decision/receipt principal is a
  function of the verified credential, independent of any `caller*` field in the
  request bytes.
- `principal_budget_isolation` — principal A's consumption cannot debit B's
  counter; a spoofed request field cannot switch the debit target.
- `receipt_principal_authenticated` — if a receipt asserts principal P, the auth
  layer accepted P for that decision (anti-spoof for auditors).

Merely proving signature verification is insufficient; the binding + isolation
theorems are the load-bearing pair.

## Explicit non-claims

- **Not** "authenticated transport ⟹ sound principal." The binding theorem is a
  separate object.
- Shared-host key custody, token theft, and confused-deputy remain outside the
  proof unless separately modelled. A bearer token readable by the MCP host
  process lets that process forge any principal it can read.
- The sharpest self-inflicted wound: shipping a **request-derived `caller_id`**
  and calling it multi-tenant. For a project whose entire value is honest-no-
  overclaim TCB, that is self-refuting and a competent evaluator catches it
  instantly.
